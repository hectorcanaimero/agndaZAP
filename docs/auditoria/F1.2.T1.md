# F1.2.T1 - Audit motor de disponibilidad

Auditoría realizada sobre `scheduling/availability.service.ts` y `scheduling/scheduling.service.ts` contra las reglas de `SPEC.md` §2.

- [P0] Herencia de BusinessHours (Fuga de slots)
  - Gap: `SPEC.md` §2 exige usar el horario del profesional "o de la clínica si el profesional no define horario". Actualmente, si el profesional define su propio horario, el motor devuelve la *unión* de los horarios del profesional y los de la clínica general.
  - Evidencia: `availability.service.ts:52-57` y `103`. La query de `businessHours` trae ambos (`OR: [{ professionalId }, { professionalId: null }]`) y el bucle iterativo (`businessHours.filter(...)`) no descarta los de la clínica cuando existen los del profesional para ese día.
  - Impacto lanzamiento: Bloqueante. Un profesional que defina trabajar solo un par de días, recibirá ofertas de turnos en todos los horarios de la clínica.
  - Recomendación: En `AvailabilityService`, después del `findMany`, agregar lógica para filtrar: si existe al menos un `BusinessHour` asociado al `professionalId`, descartar de la lista todos los que tengan `professionalId === null`.

- [P1] El buffer de limpieza/descanso no se respeta en citas activas
  - Gap: El motor suma `durationMin + bufferMin` al iterar los slots libres (paso de iteración), pero ignora el `bufferMin` de las citas *ya ocupadas* cuando evalúa solapamientos. Un slot libre generado puede solaparse con el tiempo de buffer físico de una cita anterior.
  - Evidencia: `availability.service.ts:72-88`. La query de `taken` no trae `bufferMin` del servicio de la cita, y `takenIntervals` se construye solo con `startAt` hasta `endAt` (que en DB es solo `startAt + durationMin` según `scheduling.service.ts:93`).
  - Impacto lanzamiento: Alto. Si dos servicios distintos tienen configurados diferentes duraciones y buffers, un paciente puede agendar un turno pisando el tiempo de limpieza de la cita anterior, causando demoras físicas.
  - Recomendación: En la query de `taken`, hacer `include: { service: { select: { bufferMin: true } } }` y construir el intervalo ocupado (`Interval.fromDateTimes`) haciendo que el extremo superior sea `DateTime.fromJSDate(a.endAt).plus({ minutes: a.service.bufferMin })`.

- [P2] Cumplimiento TZ y ausencia de fechas naive (Sin hallazgos críticos)
  - Gap: El spec prohíbe explícitamente usar `Date` naive. No se detectaron usos de `new Date(string)` o parseo naive. Se utiliza correctamente Luxon + timezone local de la clínica. `toJSDate()` se usa apropiadamente en transacciones hacia Prisma para enviar instantes UTC absolutos, cumpliendo con la regla de negocio.
  - Evidencia: `scheduling.service.ts:87` (comentario de código respetado) y manejos correctos con `DateTime.now().setZone(zone)`.
  - Impacto lanzamiento: Positivo (el comportamiento base es robusto).
  - Recomendación: Mantener el estándar y no requerir fixes en este frente.
