- **Task**: F1.5.T4 — Auditar `app/[locale]/admin/*` y el flujo `invite/[token]` + wizard de
  onboarding first-time (notas 2026-08-11): crear clínica, invitar admin, aceptar invitación,
  escanear QR WAHA. Revisión de completitud del flujo.
- **Artefactos contrastados**: `specs/f1-auditoria-finalizacion.md` §F1.5.T4,
  `docs/notas/2026-08-11-onboarding-wizard.md`, `docs/notas/2026-08-14-invitation-flow.md`,
  `docs/onboarding-clinica.md`, `docs/runbook-lanzamiento.md` §Bloque 6,
  `docs/adr/0014-superadmin-como-operador-saas.md`.
- **Archivos auditados**: `apps/web/src/app/[locale]/admin/**` (layout, AdminShell, dashboard,
  clinics, clinics/[id], audit, leads), `apps/web/src/app/[locale]/invite/[token]/**`,
  `apps/web/src/middleware.ts`, `apps/backend/src/admin/admin-clinics.{controller,service}.ts`,
  `apps/backend/src/invitations/**`, `apps/backend/prisma/schema.prisma` (modelo `Invitation`).

## Veredicto global

**Sin hallazgos P0.** El happy path del canary — **crear clínica → invitar admin → aceptar
invitación → escanear QR WAHA** — está completo y funcional en el branch desplegable:
`POST /admin/clinics` crea Clinic + User + Invitation en una transacción (email con fallback
de copiar link), `/invite/[token]` acepta con 204/410 idempotente y rate-limit, y el QR se
escananea desde `/panel/ajustes?tab=whatsapp` con polling adaptativo. Los guards de rol
(middleware + layout RSC + RolesGuard SUPERADMIN) están correctos y la i18n es/pt está
completa (admin 140 keys, invite 22, impersonation 13, sin gaps).

**Hay un P1 accionable**: el **wizard de onboarding first-time de 5 pasos (notas 2026-08-11)
está implementado pero viviendo en un branch sin mergear** (`feature/onboarding-wizard`), no
está en el código desplegable. A nivel operativo el flujo manual lo cubre (runbook §Bloque 6),
pero es una feature terminada y documentada como aprobada que no llegó a `main`/`staged`.

    `schema.prisma` no tiene `onboardingCompletedAt`/`onboardingProgress`, `middleware.ts` no
    tiene regla de onboarding, y no existe `PATCH /clinics/me/onboarding`. El `docs/smoke-e2e.md`
    del HEAD tampoco tiene el escenario 8 (solo el de la branch feature).
  - Evidencia: `git branch --contains 99cbfc6` → solo `feature/onboarding-wizard`;
    `git merge-base --is-ancestor origin/feature/onboarding-wizard HEAD` → false;
    `grep -n onboarding apps/backend/prisma/schema.prisma` → sin matches;
    `grep -n onboarding apps/web/src/middleware.ts` → sin matches; `apps/web/src/app/[locale]/`
    sin directorio `onboarding`; `git ls-tree -r HEAD --name-only | grep onboarding` → solo docs.
  - Impacto lanzamiento: el time-to-activation de ~5 min self-service que promete el wizard no
    está disponible; un CLINIC_ADMIN nuevo que acepta la invitación aterriza en un dashboard
    vacío y debe descubrir la configuración por sí mismo (el "widget Zeigarnik" que lo rescata
    tampoco existe). El canary manual sí funciona (runbook §Bloque 6), así que no bloquea, pero
    es una feature completa y aprobada que quedó fuera del release — decisión de producto pendiente.
  - Recomendación: revisar y mergear `feature/onboarding-wizard` sobre `staged` (rebase + review
    de los ~10 commits, verificar que la migration + backfill son additive y que el middleware

## Hallazgos P2

- [P2] No hay endpoint ni UI de "reenviar invitación" (documentado como pendiente)
  - Gap: `docs/notas/2026-08-14-invitation-flow.md` §Pendientes lista "Reenviar invitación desde
    el detalle de la clínica — endpoint `POST /admin/invitations/:userId/resend`". No existe ese
    endpoint ni botón en `AdminClinicDetailClient`. Si el email se pierde o la invitación expira
    (TTL 7 días), el SUPERADMIN no puede regenerar el link desde el panel — tiene que re-crear
    el user o tocar DB. El `InvitationsService.create()` ya tiene la semántica "borra + crea"
    lista para un resend, pero no está expuesta.
  - Evidencia: `grep -rn resend apps/backend/src` → solo `mail.service.ts` (SDK Resend) y un
    comentario en `invitations.service.ts:82`; `AdminClinicDetailClient.tsx` no tiene acción de
    reenvío; `admin-clinics.controller.ts` no expone `POST /admin/invitations/:id/resend`.
  - Impacto lanzamiento: en el canary de 40 clínicas, un admin que no recibe el email queda en
    el limbo operativo hasta que el super intervenga manualmente. Fricción de soporte real.
  - Recomendación: exponer `POST /admin/invitations/:userId/resend` en `AdminClinicsController`
    (reusa `InvitationsService.create` con `@AdminAudit`) + botón "Reenviar invitación" en el
    detalle de clínica. Fix pequeño y localizado.

- [P2] El detalle de clínica no expone el estado de la invitación (pendiente/aceptada/expirada)
  - Gap: `GET /admin/clinics/:id` no incluye la `Invitation` del primer admin (`acceptedAt`,
    `expiresAt`). El SUPERADMIN no puede saber desde el panel si el cliente ya activó su cuenta o
    si el link venció. La data está en DB (`Invitation.acceptedAt` NULL = pendiente), solo falta
    exponerla.
  - Evidencia: `admin-clinics.service.ts:302-330` (select de `get()` sin `invitations`); el listado
    tampoco la incluye.
  - Impacto lanzamiento: para operar 40 clínicas el super necesita trackear "quién ya activó";
    hoy eso exige consulta SQL directa.
  - Recomendación: agregar al `get()` un `select` de la última `Invitation` del admin (o un
    endpoint dedicado) y mostrarlo en `AdminClinicDetailClient` (badge pendiente/aceptada/expirada).

- [P2] `docs/onboarding-clinica.md` quedó desactualizado respecto al flujo admin+invitación
  - Gap: el playbook §2 dice "**Deuda documentada**: hoy no hay `POST /api/clinics`" y documenta
    el alta manual vía Prisma Studio/SQL + bcrypt CLI (§2.a-2.c). Eso quedó obsoleto: hoy existe
    `POST /admin/clinics` (SUPERADMIN) con flujo de invitación (crea Clinic + User + Invitation +
    email), y el §14 lista como deuda "`POST /api/clinics` (SUPERADMIN) — hoy via Prisma Studio"
    e "`POST /api/clinics/:id/users`" que ya están resueltos por el panel admin. El playbook es
    la referencia operativa del onboarding y sigue indicando un camino manual que ya no es el
    recomendado.
  - Evidencia: `docs/onboarding-clinica.md:42,436-437` vs `admin-clinics.controller.ts:55-70`
    (POST con invitation) y `invitations.service.ts` (create/accept).
  - Impacto lanzamiento: el operador que siga el playbook literal va a crear clínicas por SQL y a
    comunicar passwords en claro, cuando el flujo correcto es el panel admin + invitación.
    Riesgo de inconsistencia y de trazar el flujo por el camino viejo.
  - Recomendación: actualizar §2 y §14 de `docs/onboarding-clinica.md` para referenciar el panel
    admin (crear clínica → invitar admin) como camino primario y mover el alta manual a fallback.
    También sumar una nota sobre el estado del wizard (P1) y el "reenviar invitación" pendiente.

- [P2] Comentario desactualizado en `AdminClinicsClient.tsx` sobre la creación de clínicas
  - Gap: el docstring de `AdminClinicsClient` dice "La creación de clínicas (`POST /admin/clinics`)
    no está en la UI todavía — se hace vía CLI o SQL directo por ahora", pero `CreateClinicDialog`
    SÍ está montado y operativo (línea 179 del mismo archivo, con fallback de copiar link).
  - Evidencia: `AdminClinicsClient.tsx:84-88` (comentario) vs `AdminClinicsClient.tsx:179`
    (`<CreateClinicDialog locale={locale} />`).
  - Impacto lanzamiento: cosmético, pero documentación inline falsa que desorienta al próximo
    dev (y contradice el hallazgo del playbook).
  - Recomendación: borrar o reescribir el docstring.

## Sin hallazgos (verificaciones positivas)

- **Flujo de creación completo y atómico**: `POST /admin/clinics` (`admin-clinics.service.ts:172-205`)
  crea Clinic + primer CLINIC_ADMIN en una transacción; la Invitation (token 64 hex = 256 bits,
  TTL 7 días) se genera fuera de la txn (`:210-213`) y el email es fire-and-forget con `emailSent`
  en el response para que el UI abra el dialog de copiar link si falla (`CreateClinicDialog.tsx:114-129`).
  El password inicial es random + bcrypt y NUNCA se expone (`:168-170`). Coincide con notas 2026-08-14.
- **Aceptación de invitación correcta**: `GET /api/public/invitations/:token` devuelve solo info
  safe (email, invitedName, clinicName, expiresAt — sin userId/clinicId/invitedBy) con 404/410
  (`invitations.service.ts:86-121`); `POST .../accept` valida password (min 8, max 128), hashea
  fuera de la txn y persiste password+acceptedAt atómicamente con idempotencia 410
  (`:131-158`). Rate-limits por IP 30/min GET y 10/min POST (`invitations.controller.ts:44,61`).
- **Página `/invite/[token]` correcta**: server component que mapea 404 → "enlace inválido",
  410 → "expirado/usado", y cualquier otro error → inválido (sin fugar detalles del backend,
  `page.tsx:48-79`). NO usa el `fetcher()` con redirect a login (es público). El form client
  valida password + confirm con zod, muestra la cuenta activada con botón "Ir al login" en vez
  de auto-redirect (decisión UX documentada en `InviteAcceptForm.tsx:52-55`).
- **QR WAHA alcanzable desde el panel**: el paso "escanear QR" del canary se cumple vía
  `/panel/ajustes?tab=whatsapp` (WhatsApp vive como tab de Ajustes; `/panel/config/whatsapp`
  redirige a `ajustes?tab=whatsapp`, `page.tsx:17`). `WhatsappConnectionClient` hace polling
  adaptativo (3s transitorio / 15s WORKING / off terminal), muestra el QR embebido en
  `SCAN_QR_CODE`, maneja 429 con backoff y 502 sin romper el loop, y usa ConfirmDialog para
  desconectar. Coincide con ADR 0008.
- **Guards de rol en 3 capas para `/admin/*`**: middleware (`middleware.ts:42-62`, SUPERADMIN
  requerido, role distinto → panel), layout RSC (`admin/layout.tsx:32-42`, redirige login/panel y
  force-logout en 401) y RolesGuard SUPERADMIN en el backend (`admin-clinics.controller.ts:42-44`).
  El impersonation token solo puede usarse en `/panel/*` (rol degradado a CLINIC_ADMIN) — ver
  reporte F1.4.T4.
- **i18n es/pt completa en el flujo auditado**: `admin` 140 keys, `invite` 22 keys,
  `impersonation` 13 keys — cero es-only / pt-only en los tres namespaces. El namespace
  `onboarding.*` existe solo en la branch feature (consistente con el hallazgo P1).
- **Estados de UI del admin correctos**: listados con loading/error/empty + retry, paginación,
  filtros por status, ConfirmDialog para acciones destructivas (suspend/reactivate), dialog con
  motivo obligatorio para suspender, y el detalle muestra banner de suspensión con motivo. Sin
  `confirm()` nativo.
